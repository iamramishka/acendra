## Reproduction

Full local Supabase: set `ACENDRA_LOCAL_PORT_BASE=60000`, run `node tool/local_supabase.mjs start test`, then `node tool/csa197_benchmark.mjs`. The existing helper hashes the worktree identity into the stack name; the benchmark selects only that exact database container and rejects remote Docker sockets. Stop with the same local helper/profile afterward.

Native fallback used here:

1. Initialize a fresh PostgreSQL 17 cluster under this worktree's ignored `build/csa197-pg` with `initdb -U postgres -A trust --encoding=UTF8 --locale=C`.
2. Start with `pg_ctl -D build/csa197-pg -l build/csa197-pg.log -o "-h 127.0.0.1 -p 60011" -w start`. Create `csa197_benchmark` using loopback port 60011.
3. Run `tool/csa197_native_bootstrap.sql` with psql `-v ON_ERROR_STOP=1`, then replay all sorted `supabase/migrations/*.sql` with the same fail-on-error option.
4. Set `CSA197_NATIVE=1`, `CSA197_DISPOSABLE=csa197_benchmark`, `CSA197_DATABASE=csa197_benchmark`, `CSA197_PORT=60011`, and `CSA197_PSQL` to the local psql executable. Run `node tool/csa197_benchmark.mjs`. The output artifact is `build/csa197-results.json`.
5. Stop only this cluster with `pg_ctl -D build/csa197-pg -m fast -w stop`.

The native connection fixes host to 127.0.0.1 and database to the acknowledged disposable name; inherited PG*/SUPABASE_* variables are removed. It does not reset databases, disable RLS, or suppress SQL failures. Never point it at a live/shared database. Native shims intentionally omit actual Auth sessions, service runtime and storage transport.

## Limits and next review

Docker CLI exists but its local engine socket was unavailable; no full Supabase benchmark was claimed. Native measurements use the actual repository tables, indexes, grants, policies and account eligibility functions, but shimmed Auth functions/tables. Dataset setup as postgres does not time privileged queries: timed queries execute after SET LOCAL ROLE authenticated with RLS enabled.

Warm-cache, single-client timings on this development machine are a local baseline, not production capacity. No checkout/finalization mutation, bank queue, protected media RPC, cold-cache, concurrent workload or hosted PostgREST transport was measured. SRS's proposed catalog API P95 below one second is not an approved SQL threshold and cannot be inferred from these numbers. Review realistic workloads and rerun full Supabase/hosted staging measurements before claiming API latency or production readiness. No index/schema change is justified from this small baseline alone.
