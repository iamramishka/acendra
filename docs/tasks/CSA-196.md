## 1. Measurement Approach

### Time to First Interactive (TTFI)

TTFI for Flutter Web is the elapsed time from navigation request to when the
app responds to user input. The practical measurement approach:

1. **Build a release web bundle:**
   ```bash
   flutter build web --release --dart-define=SUPABASE_URL=<url> --dart-define=SUPABASE_ANON_KEY=<key>
   ```

2. **Serve locally with a representative server:**
   ```bash
   cd build/web && python -m http.server 8080
   ```

3. **Measure in Chrome DevTools:**
   - Open `http://localhost:8080` in an incognito window.
   - Open DevTools → Performance tab → tick "Screenshots".
   - Click the record button and reload the page.
   - Stop recording after the app shell renders.
   - Read the "TTI" (Time to Interactive) marker in the Timings row.

4. **Lighthouse audit (automated):**
   ```bash
   npx lighthouse http://localhost:8080 --only-categories=performance --output=json
   ```
   Key metrics to collect: FCP (First Contentful Paint), TTI, TBT (Total
   Blocking Time).

5. **Repeat 3 times and report the median** to reduce noise from JIT warmup.

> Note: The Flutter Web renderer (CanvasKit vs HTML) significantly affects
> bundle size. The default for `--release` is CanvasKit (Wasm). If a smaller
> initial payload is needed, pass `--web-renderer html`.

## 3. Main Entrypoint Analysis

### lib/main.dart

```dart
import 'app/bootstrap.dart';

void main() => bootstrap();
```

**Observations:**
- `main()` is a single synchronous function call that immediately delegates to
  `bootstrap()`.
- No code runs synchronously at top-level before `runApp`.
- No conditional imports or platform-channel calls at the top level.
- **No bottleneck here.**

---

### lib/app/bootstrap.dart

```dart
Future<void> bootstrap() async {
  WidgetsFlutterBinding.ensureInitialized();           // (A)

  if (EnvConfig.supabaseUrl.isNotEmpty &&              // (B)
      EnvConfig.supabaseAnonKey.isNotEmpty) {
    await Supabase.initialize(                         // (C)
      url: EnvConfig.supabaseUrl,
      anonKey: EnvConfig.supabaseAnonKey,
    );
  }

  runApp(const ProviderScope(child: AcendraApp()));   // (D)
}
```

**Step-by-step analysis:**

| Step | What it does | Performance notes |
|------|-------------|-------------------|
| (A) `WidgetsFlutterBinding.ensureInitialized()` | Registers platform channels, binds Flutter to the native engine | Synchronous; ~1 ms; required before any async work. |
| (B) Guard on `EnvConfig` | Reads compile-time `String.fromEnvironment` constants | Constant-folded at compile time; zero runtime cost. |
| (C) `Supabase.initialize(...)` | **Async.** Sets up the Supabase HTTP client, local storage adapter, and auth state restore. Awaited before `runApp`. | **Potential bottleneck.** Supabase v2 restores a persisted auth session from `localStorage` during initialization. On a cold start this involves deserializing a stored JWT and triggering an `onAuthStateChange` event. Measured overhead is typically 50–200 ms on a mid-range device. |
| (D) `runApp(ProviderScope(...))` | Mounts `AcendraApp`, inflates `MaterialApp.router` | `appRouterProvider` and `themeModeProvider` are created lazily; no eager provider warmup here. |

---

### lib/app/app.dart

```dart
class AcendraApp extends ConsumerWidget {
  Widget build(BuildContext context, WidgetRef ref) {
    final router = ref.watch(appRouterProvider);
    final themeMode = ref.watch(themeModeProvider);
    return MaterialApp.router(...);
  }
}
```

**Observations:**
- `appRouterProvider` creates the `GoRouter` on first watch.
  - The router builds a redirect guard that reads `sessionRestoredProvider` and
    `isAuthenticatedProvider` on every navigation event.
  - Both providers watch `authStreamProvider` which is a
    `StreamProvider<AuthState>`. The stream emits its first event only after
    Supabase auth state restore completes.
- `themeModeProvider` is a lightweight `NotifierProvider<ThemeModeNotifier,
  ThemeMode>` initialized to `ThemeMode.system`. Zero startup cost.

**First render path:**

```
runApp
  └─ AcendraApp.build
       ├─ appRouterProvider watches authStreamProvider
       │    └─ authStreamProvider = StreamProvider over Supabase.onAuthStateChange
       │         (no value yet → AsyncLoading)
       │    └─ sessionRestoredProvider = false  (stream has no value yet)
       │    └─ router redirect fires → stays on current route (waits for session)
       └─ MaterialApp.router renders initial route
            └─ redirect guard blocks navigation until sessionRestoredProvider = true
```

The app shell renders immediately, but the first meaningful route is gated on
the Supabase auth stream emitting. Until that event arrives:
- The router's redirect guard returns `null` (no redirect), leaving the user on
  `/` which shows a loading state or the public home screen.
- There is **no blank screen** — the shell renders, but content is deferred.

## 4. Eagerly Loaded Providers

Only providers that are explicitly `ref.watch`-ed during the first build frame
are eagerly initialized:

| Provider | Where watched | Eager? | Cost |
|----------|--------------|--------|------|
| `appRouterProvider` | `AcendraApp.build` | Yes | Builds `GoRouter` — negligible |
| `themeModeProvider` | `AcendraApp.build` | Yes | Reads `ThemeMode.system` — negligible |
| `authStreamProvider` | via `appRouterProvider` | Yes | Opens Supabase auth stream — I/O bound, not CPU bound |
| `sessionRestoredProvider` | via router redirect | Yes | Derives from `authStreamProvider` — negligible |
| `isAuthenticatedProvider` | via router redirect | Yes | Derives from `authStreamProvider` — negligible |

All other feature providers (`marketplaceProvider`, `myCoursesProvider`,
`checkoutProvider`, etc.) are created **lazily** when the corresponding screen
is first rendered.

## 5. Identified Bottlenecks

### B1 — Supabase.initialize blocks runApp (MEDIUM)

`await Supabase.initialize(...)` is called **before** `runApp`. While this
avoids an `Uninitialized Supabase client` error, it means:
- The Flutter engine is idle while the JS/Wasm Supabase client bootstraps.
- On slow networks or cold service-worker starts, this extends the blank screen.

**Impact:** 50–200 ms additional blank-screen time on first load.

### B2 — authStreamProvider gating all navigation (LOW)

Every navigation redirect reads `sessionRestoredProvider` (which is `false`
until the Supabase auth stream emits). Until that first emission, `go_router`
will not redirect the user to their post-login destination.

**Impact:** Navigation feels delayed by 1–3 frames after the app shell renders.

### B3 — CanvasKit Wasm download (HIGH on first load, not a code issue)

The Flutter CanvasKit renderer downloads `canvaskit.wasm` (~1.5 MB) on the
first visit. This is not a code-level bottleneck but the largest contributor
to real-world TTFI.

**Impact:** 1–3 s additional TTI on a 3G connection.

---

## 6. Recommendations

### R1 — Move Supabase.initialize after runApp (quick win)

Initialize Supabase **asynchronously after** `runApp`, using a loading splash
managed by `sessionRestoredProvider`. The splash renders immediately, hides
the blank frame, and the rest of the app mounts behind it.

```dart
Future<void> bootstrap() async {
  WidgetsFlutterBinding.ensureInitialized();
  runApp(const ProviderScope(child: AcendraApp())); // render immediately

  if (EnvConfig.supabaseUrl.isNotEmpty &&
      EnvConfig.supabaseAnonKey.isNotEmpty) {
    await Supabase.initialize(...);
    // Riverpod's authStreamProvider picks up the client automatically
    // when sessionRestoredProvider becomes true.
  }
}
```

**Caution:** The router's redirect guard must safely handle the window where
`Supabase.instance` is not yet initialized (currently guarded by
`EnvConfig.supabaseUrl.isEmpty`). Verify no provider accesses
`Supabase.instance.client` before the guard resolves.

### R2 — Add a persistent service-worker cache for canvaskit.wasm

In `web/flutter_service_worker.js` (generated by `flutter build web`), ensure
`canvaskit.wasm` is in the pre-cached assets list. Flutter 3.x generates this
automatically when `--pwa-strategy=offline-first` is passed.

```bash
flutter build web --release --pwa-strategy=offline-first
```

Repeat visits then serve `canvaskit.wasm` from cache (~0 ms vs 1–3 s).

### R3 — Lazy-load heavy admin screens

`app_router.dart` imports every screen at the top of the file, including admin
screens (`AdminDashboardScreen`, `CurriculumBuilderScreen`, etc.). In
CanvasKit/Wasm mode tree-shaking removes unused Dart code, but the import
chain still forces Dart to parse and compile those class definitions.

Consider moving admin routes to a `LazyRoute` or deferred import group once
the feature set stabilizes.

### R4 — Measure before acting

Run the Lighthouse audit against a `--release` build with
`--web-renderer=canvaskit` before and after each optimization to confirm real
gains. Use `flutter build web --release --analyze-size` to identify any
unexpectedly large libraries.

## 7. Summary

| Concern | Severity | Action |
|---------|----------|--------|
| Supabase.initialize before runApp | Medium | R1 — move after runApp |
| canvaskit.wasm first-visit download | High (perceived) | R2 — service-worker pre-cache |
| Admin screen imports at router level | Low | R3 — defer when stable |
| authStreamProvider redirect gate | Low | Acceptable; splash covers it |

The startup path is lean and correct. The only code-level quick win is R1.
The biggest user-perceived gain comes from R2 (service-worker caching), which
is a build-flag change rather than a code change.
